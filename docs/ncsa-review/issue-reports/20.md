## Limits of the part 1 test
The test reads the bytes on disk at the moment `Lock.release` is called, then asserts valid JSON containing the row, then the order fsync, replace, release. It fails on the old code in all 8 cases, but on Windows the failure is `PermissionError(13)`, because the old code locks the data file itself and the test cannot read it. So on this machine it did not observe the empty or partial buffer the issue describes. On the fix it shows the complete document at release. The buffered-data failure itself has still not been observed here.

## Behavior changes to review
- Existing store on a read-only volume: reads now need to open the sidecar lock file, so they raise instead of being served. A missing file still returns the default and creates nothing.
- Lock failures and `OSError` in `storage.load` now raise (500) rather than returning the default, because the catch was removed as the plan says.
- New files in `var/`: `<name>.lock` persists, and `<name>.json.tmp` can remain after a crash until the next write. `var/` is gitignored.
- Risk, not tested: the main checkout's `var/` is under OneDrive. On Windows, a sync client or antivirus holding a handle could make `os.replace` raise `PermissionError`, giving a 500 with the previous document intact. No retry was added.
- The directory is not fsynced after `os.replace`, so a power loss can lose the newest write, though not corrupt the document.
- `audit.jsonl` still uses in-place append under portalocker, per the proposals' "not affected". The same unlock-before-close ordering applies to it, so a reader could miss the newest line.
